# GraphRAG 学习笔记：从用户提问到两跳检索与原文引用

上一篇 [《一份文档怎样变成一张可追溯的图》](document-to-graph.md) 讲的是怎样从文档抽取事实、对齐实体，并保存每条关系的出处。这一篇走查询方向。用户只问了一句“林晨所在部门的负责人是谁？”，系统需要从“林晨”找到正确的人，从任职关系查到部门，再拿着同一个部门的编号查出负责人。最后还要找到能支持这两步的原文。

**RAG（Retrieval-Augmented Generation，检索增强生成）**是在生成答案前先找资料，再把相关资料提供给语言模型。**GraphRAG（基于图的检索增强生成）**是在检索流程里利用节点和关系组织、查找相关信息的方法。本文用一条明确的两跳路径讲查询机制。微软的 GraphRAG 是同名的一个具体项目，它有面向具体实体的局部搜索，也有利用图中实体群摘要回答全库问题的全局搜索。 [微软 GraphRAG 查询概览](https://microsoft.github.io/graphrag/query/overview/) · [Neo4j GraphAcademy 教程](https://graphacademy.neo4j.com/knowledge-graph-rag)

## 1. 查询开始前，系统里有哪些数据？

继续使用上一篇的虚构材料。两份文档来自同一家公司的同一编号体系，例子里的版本都是 v1。

| 出处 | 原文 |
| --- | --- |
| 《员工目录》A1 | 林晨（员工编号 E017）于 2024 年 5 月 6 日入职。 |
| 《员工目录》A2 | 自 2025 年 1 月 1 日起，林晨任职于客户支持部（部门编号 D012）。 |
| 《员工目录》A3 | 该部门在本目录中也称“客服部”。 |
| 《部门负责人名单》B1 | 客服部（部门编号 D012）的部门负责人为周宁（员工编号 E021）。 |

上一篇已经对齐了 A2 的“客户支持部”和 B1 的“客服部”。在图中，两处提及指向同一个部门节点 D012。图里存下了两条业务关系。

```text
林晨 E017 ──任职于──→ 客户支持部 D012 ←──负责── 周宁 E021
```

查询会用到三种可查的数据。它们可以存在同一个系统，也可以分开保存。

| 数据 | 本例中的内容 | 查询时的用途 |
| --- | --- | --- |
| 实体索引 | 姓名、别名、类型、编号与图中对象的对应表 | 从问题中的“林晨”找到员工 E017。 |
| 关系记录 | E017 任职于 D012；E021 负责 D012 | 按对象、关系类型和方向逐跳查找。 |
| 证据记录 | 每条关系关联的文档 ID、版本和原文位置 | 找回 A2、B1，核对关系；需要时取 A1 复核员工身份。 |

**索引**是为了按某些条件更快查到记录而准备的数据结构。**Chunk（文本块）**是系统索引或检索的一段文本，可以包含多个句子。系统可以先按 ID 读出包含 A2 的文本块，再定位到 A2 原句。存入时保留的粒度决定回查时能定位到哪里。 [微软 GraphRAG 索引输出字段](https://microsoft.github.io/graphrag/index/outputs/)

## 2. 查询理解：把问题拆成要找的对象和关系

> 林晨所在部门的负责人是谁？

**查询理解**是把自然语言问题转成系统可以据以查找的信息。它要区分用户已经给出的内容、需要查出的内容，以及影响结论的限制条件。

| 解析项 | 本题的结果 |
| --- | --- |
| 已知对象 | “林晨”，预期是员工。 |
| 中间对象 | 林晨任职的部门，部门名称未知。 |
| 最终目标 | 担任该部门负责人的员工，姓名未知。 |
| 时间条件 | 没有指定日期；“所在”可能带有现状含义，答复需明确资料的适用范围。 |

**Schema（模式）**是图中对象类型、字段、关系含义与方向的规则。这里把“所在部门”对应到 `员工 → 任职于 → 部门`，把“负责人”对应到 `员工 → 负责 → 部门`。两种关系都指向部门，但查询时第二步是拿已知部门反查负责人。

**查询计划**是系统准备执行的查找步骤。本例可以表示成“定位林晨 → 找任职部门 → 按部门查负责人 → 回查每条关系的出处”。问题理解阶段只需要确定怎么查；D012、E021 等查找结果由数据填入。如果问法稳定，系统可以用预先定义的查询模板。如果要让模型把自然语言转成数据库查询，可以使用 **Text-to-Cypher**，其中 **Cypher** 是 Neo4j 用来查询节点、关系和属性的语言。模型生成的查询也需要受可访问范围、允许关系与查询开销的约束。 [Neo4j GraphAcademy 的图查询教程](https://graphacademy.neo4j.com/knowledge-graph-rag)

## 3. 实体定位：从用户说的“林晨”到图里的 E017

**提及（Mention）**是文本中指向某个对象的表达，“林晨”在问题里就是一个提及。**查询侧实体链接（Entity Linking）**是把这个表达连到图中的具体对象。用来进入图并开始查找的节点，叫**种子节点（Seed Node）**。

### 3.1 先召回可能的人

**召回**就是找出值得进一步检查的候选。入口可以不同。

| 用户给出的线索 | 怎样找候选 |
| --- | --- |
| “E017” | 在正确的公司和员工编号范围内查这个编号。 |
| “林晨” | 查员工姓名或别名，可能召回多位同名员工。 |
| 使用口语或角色描述 | 可以用向量检索比较问题与实体描述的含义，或先找相关文本，再从文本中的已链接提及进入图。 |

**向量检索**是把查询和文本或实体描述转换成数字表示，再按表示的相似度找候选。相似度能提供线索，具体身份还要结合名称、类型、编号和上下文核对。微软的 Local Search 会用实体描述的向量找到相关实体，再收集关系、文本单元等信息。Neo4j 的教程也展示了从相似文本块进入图的模式。 [微软 Local Search 流程](https://github.com/microsoft/graphrag/blob/main/docs/query/local_search.md) · [Neo4j GraphAcademy 教程](https://graphacademy.neo4j.com/knowledge-graph-rag)

### 3.2 再消歧，确定起点

**消歧（Disambiguation）**是从多个合理候选中判断问题指的是谁。在本例限定的可查范围里，“林晨”只有一个匹配的员工 E017，A1 记录了姓名与编号的对应。若同一公司有 E017、E042 两位林晨，可以利用用户已经给出的工号、已知组织范围或对话中确认过的身份。线索仍不足时，需要澄清是哪一位。

这里还有两个不同的对齐动作。**文档构建时**，我们用 A1 和目录上下文把 A2 里的“林晨”连到 E017。**问答时**，我们再把用户问题里的“林晨”连到 E017。两者都涉及身份，但输入和证据来源不同。起点选错后，哪怕后面的部门和负责人关系都查得准确，答案也会属于另一位员工。

## 4. 两跳检索：把上一跳的结果用作下一跳的条件

**图遍历**是从已知节点出发，按条件沿边查找相邻节点。走过一条边叫**一跳**，连续走过多条边叫**多跳**。这些连续连接的节点和边组成一条**路径**。

| 步骤 | 输入 | 查找条件 | 输出 |
| --- | --- | --- | --- |
| 第一跳 | 员工 E017 | 查从 E017 发出的 `任职于` 边，目标类型为部门。 | 部门 D012，任职从 2025-01-01 起，关系出处 A2。 |
| 第二跳 | 部门 D012 | 查指向 D012 的 `负责` 边，边的来源类型为员工。 | 员工 E021，姓名周宁，关系出处 B1。 |

**出边**是从当前节点发出的边，**入边**是指向当前节点的边。第二跳是拿 D012 查入边。数据库里保存的业务事实仍然是“周宁负责 D012”。可以从关系两端查询，关系本身的语义方向保持一致。

### 4.1 为什么 D012 比部门名称更适合接力？

B1 只写“客服部”，也没出现“林晨”。如果只用原问题找相似文本，B1 有可能排得靠后。图查询从 A2 得到 D012，直接找连接到该节点的负责人关系。名称不同也能接上，前提是两份资料确实使用同一个部门身份。若编号来自不同组织，需先核对编号的发行范围，不能只凭字符串 D012 相同就连接。

普通文本 RAG 也可以拆成两次搜索，先找林晨的部门，再搜该部门的负责人。这里图提供了明确的中间对象、可限制的关系类型和查询方向。优势是否体现，取决于图里的关系是否覆盖问题，以及实体对齐是否正确。 [Neo4j Labs 的图检索模式](https://neo4j.com/labs/genai-ecosystem/graphrag/)

### 4.2 查到多个结果时怎样筛选？

真实系统里，林晨可能有历史调岗记录，一个部门可能有多任负责人。此时应保留仍可能成立的路径，再检查两条关系是否覆盖同一查询时期。例如某人 2025 年才调入，名单却只对 2024 年有效，就不能将两条记录合成 2025 年的负责人答案。只有开始日、没有明确结束状态的记录，也不足以单独确认当前情况。

**跳数上限**控制路径走多深；**Top K** 指在某个步骤至多保留排名靠前的 K 个候选。两跳可以查出多条路径，也可以关联多段原文。在本题中，优先按边的类型和方向查找，再用时间与范围缩小候选，能减少因部门同时连着大量员工、项目和制度而产生的无关结果。

## 5. 证据回查：从边找到原文，再核对原文支持什么

**证据回查**是沿着图谱记录保存的出处取回原文，并核对它是否支持当前要回答的判断。**溯源**还包括知道这条记录来自哪份文档、哪一版，以及采用了什么定位。可以用一条关系 ID 对应多条证据，每条证据注明支持的是关系本身、对象身份，还是时间等限定信息。

### 5.1 逐跳取回原句

| 要核对的判断 | 如何定位 | 要读哪部分 |
| --- | --- | --- |
| 第一跳：E017 任职于 D012 | 任职关系的证据指到 `doc-a / v1 / A2`。 | 读 A2 整句。“自……起”给出这次任职的生效日，括号给出部门编号。只高亮“林晨任职于客户支持部”会遗漏日期和编号。 |
| 第一跳的身份依据：A2 中的林晨是 E017 | 关系或提及的辅助证据指到 `doc-a / v1 / A1`。 | A1 给出姓名和工号，结合目录上下文确认同一人。A1 中的 2024-05-06 是入职日期。 |
| 第二跳：周宁 E021 负责 D012 | 负责关系的证据指到 `doc-b / v1 / B1`。 | 读 B1 整句，同时核对负责人姓名、工号和部门编号。句中没有任期信息。 |
| 两跳能否接在一起 | 对照 A2 与 B1 的 D012，以及两份资料的编号体系。 | 两边必须是同一部门。需要解释称呼差异时，可以取 A3 补充目录内的简称。 |

回查时还要检查原文版本、可见范围和文档是否仍可用。比如一份旧名单被停用，图上可能暂时还留着它抽取出的关系；若已没有用户可用的出处，该关系不能直接写成有据的结论。**节点关联片段**只说明文本曾提到某个对象。要证明“周宁负责 D012”，应优先取支撑这条具体关系的片段，并核对文本表达的含义。

微软 GraphRAG 公开索引中，关系记录的 `text_unit_ids` 指向相关文本块，文本块的 `document_id` 指向源文档。那是块级出处的例子。本文在其基础思路上演示句子编号和具体证据用途，便于把每条判断解释给用户。 [微软 GraphRAG 索引输出字段](https://microsoft.github.io/graphrag/index/outputs/)

### 5.2 粗排与精排还要照顾两跳证据

**粗排**是从较多候选中快速筛出一批值得细看的结果。**精排**是在较小的候选集里进一步判断哪些结果真正有用。如果图检索、关键词检索和向量检索同时返回文本，可以先按文档版本与位置去重，再排序。

两跳题要额外检查**证据覆盖**，即支撑答案的每个关键步骤都有至少一条可用的证据。比如 A2 和另外三段员工资料都和“林晨”高度相关，B1 却因没有写林晨而分数靠后。若只按单段相关性取前几条，很可能留下四段员工资料，却丢掉负责人证据。可以先从每一跳的候选里保留一条直接证据，再用剩余空间补充身份、别名等上下文。证据仍不足时，要把缺口保留到答案阶段。 [上一篇检索笔记中的候选融合与精排](../rag/retrieval-and-reranking.md)

## 6. 生成答案：先确定能说什么，再组织语言

**上下文（Context）**是生成时提供给语言模型的信息。这里可以把用户问题、检索到的路径、逐跳原文及其可引用的出处组织在一起。**引用**把答案中的一句话对应到具体原文，方便读者回查。

本题的一次查询可以整理成下面这份简短输入。示意中省略了已经核实的完整原句，实际给模型时要保留原句与来源定位。

```text
问题：林晨所在部门的负责人是谁？
已定位的员工：林晨 E017，姓名与工号见 A1
第一跳：E017 任职于 D012，关系与生效日期见 A2
第二跳：E021 负责 D012，姓名周宁及部门编号见 B1
适用范围：B1 给出名单所列负责人，未给负责人任期
生成要求：逐项注明原文出处；时间范围不明时按来源表述
```

可输出的答案是：

> 《员工目录》记载，林晨自 2025 年 1 月 1 日起任职于客户支持部（D012）。【A2】《部门负责人名单》所列的 D012 负责人是**周宁**。【B1】

模型可以把结构化结果写成自然语言。生成后还可以做一次**引用核验**，检查每处引用是否存在、读者是否有权访问，以及相应原文是否支持答案里的名字、关系与时间。比如把整句“林晨所在部门的负责人是周宁”只标成【A2】，会让读者在 A2 找不到负责人。拆成两句分别引用，或给组合判断同时标两处来源，都能把依据交代完整。

| 检索或提问出现的变化 | 答案如何处理 |
| --- | --- |
| 找到 A2，没找到可用的 B1 | 可以说明资料记载的任职部门，再明确现有资料不足以确认负责人。 |
| 用户问“现在还是周宁吗？” | 查当前适用的任职与负责人记录。例文缺少足以确认现状的时间信息，可以说明名单中列的是周宁。 |
| 两份名单同一时期分别写周宁和另一位员工 | 核对版本、职责和适用范围。冲突仍在时，列出不同来源及各自说法。 |
| 用户问“周宁是林晨的直属上级吗？” | 另查直属汇报关系，或核对适用的组织规则。现有资料支持部门负责人身份。 |
| 发现起点存在两个同名员工 | 回到实体定位，结合已有线索消歧；仍无法确定时，请用户给出工号或其他可区分信息。 |

## 7. 对照国内外实现，区分图在查询中做了什么

| 实现 | 怎样进入图 | 图用来做什么 |
| --- | --- | --- |
| 腾讯 WeKnora 常规聊天管线 | 从问题提取实体名，再按名称查图。 | 查匹配节点和一跳邻居，取节点关联的原文分块，去重后补入检索候选。 [WeKnora 图谱增强说明](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/09-knowledge-graph.md) · [实体检索源码](https://github.com/Tencent/WeKnora/blob/main/internal/application/service/chat_pipeline/search_entity.go) |
| 微软 GraphRAG 的 Local Search | 用实体描述的向量定位相关实体。 | 取相关关系、文本块等候选，筛选后组织为模型上下文。 [微软 Local Search 文档](https://microsoft.github.io/graphrag/query/local_search/) |
| Neo4j 的向量加图查询模式 | 先通过向量检索定位节点。 | 用后续 Cypher 查询读取所需关系或相邻对象，具体查哪些由查询定义。 [Neo4j GraphRAG 检索器文档](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html) |

本文的两跳流程是一种教学用查询方案。它把 `任职于` 和 `负责` 明确写成连续查询，并逐条回查原文。阅读项目文档时，可以分别检查入口是什么、查到了哪些关系、返回的是节点关联文本还是关系出处，以及答案生成前如何利用这些材料。

## 8. 复习时，按输入和输出走一遍

| 问题 | 可以怎样回答 |
| --- | --- |
| 用户只说了“林晨”，系统怎样找到 E017？ | 抽取姓名提及，在可查询范围内查名称候选，按类型、编号或上下文消歧，再链接到 E017。 |
| 为什么这是两跳？ | 第一条边把 E017 连到 D012；第二次从 D012 沿指向它的 `负责` 入边查到 E021。 |
| 为什么原问题没出现周宁也能找到他？ | 第一跳得到 D012，第二跳以同一个部门 ID 查负责人，周宁是数据返回的目标。 |
| 怎么判断答案有两跳证据？ | A2 支持任职、时间和部门编号，A1 辅助确认员工身份，B1 支持名单里的负责人。还要核对 D012 指的是同一个部门。 |
| 如果只返回 B1，能回答原问题吗？ | B1 能回答“名单中的 D012 负责人是谁”。它缺少把林晨和 D012 接起来的 A2。 |
| 能说“周宁现在是林晨的直属上级”吗？ | 现有文档只支持任职部门和名单所列负责人。要回答现状或直属汇报关系，需要对应的时间证据或组织关系证据。 |
