# 知识图谱的信息抽取：方法选择与开放式抽取实战

[图谱构建篇](document-to-graph.md)用《员工目录》说明了怎样从文档得到实体、关系和原文证据。这篇聚焦其中的**信息抽取**，也就是把原文里的描述转成程序可以处理的字段。我们先看有哪些抽取方法，再用一段展览介绍走完开放式抽取的过程，包括 Python 如何填入正文、模型应该返回什么，以及怎样核对结果。

## 1. 一个 Chunk 里要抽什么？

**Chunk（文本块）**是一次送去处理的一段文字，可以包含一个或多个句子。继续用《员工目录》中的 A2：

> 自 2025 年 1 月 1 日起，林晨任职于客户支持部（部门编号 D012）。

| 信息 | 本例抽到什么 | 判断依据 |
| --- | --- | --- |
| 实体提及 | 林晨、客户支持部 | **提及**是原文里指向某个对象的文字。这里的对象分别是人和部门。 |
| 实体属性 | 客户支持部的部门编号为 D012 | 编号描述部门本身。 |
| 关系 | 林晨 → 任职于 → 客户支持部 | 原句明确说明两者之间的任职关系。 |
| 关系的限定信息 | 任职生效日期为 2025-01-01 | 日期修饰这次任职。A1 的 2024-05-06 描述的是林晨入职公司的时间。 |
| 原文证据 | A2 整句 | 整句包含关系、部门编号和日期。 |

只看 A2，能识别出“林晨”这个名字。要把它对应到图里的员工 E017，还需要 A1 和目录上下文。把原文中的提及对应到具体对象，叫**实体链接**。抽取回答“这里提到了什么、说了什么”，实体链接回答“说的是哪一个对象”。把 Chunk 作为处理单位时，要留意身份、指代和关系的证据可能落在相邻句子里。

## 2. 大模型是其中一种抽取方法

| 方法 | 怎样做 | 适合什么来源 |
| --- | --- | --- |
| **直接映射字段** | 人事表如果已经有员工编号、部门编号和任职开始日，就按字段含义将一行映射为两个节点、一条边及其日期。 | 数据库、API、字段明确的 Excel。重点是核对字段的业务含义和编号范围。 [W3C 关系数据库到 RDF 的映射规范](https://www.w3.org/TR/r2rml/) |
| **词典、规则和模板** | 用部门词典匹配名称，用“部门编号”及编号格式找 D012，再用“自某日起，某人任职于某部门”的句式找关系和日期。 | 格式稳定的目录、通知和表单。遇到“调入”“转岗至”等写法，需要判断业务含义，再决定是否扩充规则。 [spaCy 规则识别](https://spacy.io/api/entityruler) · [Stanford CoreNLP 关系规则](https://stanfordnlp.github.io/CoreNLP/kbp.html) |
| **专用抽取模型** | 用 **NER（命名实体识别）**定位人名、机构名等文字，再用 **RE（关系抽取）**判断对象之间表达了什么关系。两个任务可以分开做，也可以由同一个模型一起做。 | 实体和关系类型相对稳定，可以准备标注样本或验证已有模型在目标文本上的效果。 [实体与关系分阶段抽取研究](https://aclanthology.org/2021.naacl-main.5/) · [PaddleNLP 信息抽取](https://paddlenlp.readthedocs.io/en/stable/model_zoo/taskflow.html) |
| **通用大模型抽取** | 把任务要求和文本块送给模型，要求返回实体、属性、关系、方向和证据。 | 来源多、写法灵活、需要结合上下文识别信息的正文。输出后还要核对原文是否支持每条记录。 [WeKnora 图谱构建说明](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/09-knowledge-graph.md) |

这些方法可以组合使用。例如从员工表读取工号，从正文抽取“任职于”，再用上下文把人名连到正确工号。在 WeKnora 的入库流程中，启用图谱后，系统会选择适合抽取的文本块，组装指令和示例后交给 Chat 模型，再解析模型输出。它的默认指令在 `config/config.yaml` 的 `extract.extract_graph` 下，明确要求从指定列表选择关系类型。微软的 Standard GraphRAG 也提供了公开模板，包含实体类型、关系说明、输出格式和输入输出示例。 [WeKnora 抽取提示词](https://github.com/Tencent/WeKnora/blob/main/config/config.yaml#L49-L86) · [微软 GraphRAG 抽取提示词](https://github.com/microsoft/graphrag/blob/main/packages/graphrag/graphrag/prompts/index/extract_graph.py)

另一种建图方法用**共现**建立连接。共现指两个对象在同一个文本单元里一起出现。比如“林晨参加了客户支持部的例会”支持两者共现，也表达了参会事实。若要写入 `任职于`，仍需 A2 这样的证据。微软 FastGraphRAG 使用名词短语在文本单元中的共现建立边，可以帮助查找相关内容。读到这类边时，要按共现的含义理解。 [微软 GraphRAG 索引方法](https://microsoft.github.io/graphrag/index/methods/)

## 3. 开放式抽取允许模型自己提出业务标签

**Schema（模式）**在这里指业务上允许的实体类型、属性、关系及其方向。按 Schema 抽取时，可以事先规定只抽“员工”“部门”“任职于”“负责”。当项目会处理多种文本时，也可以让 Python 每次把对应的 Schema 填进同一份提示词。

**开放式抽取**让模型根据原文自己提出类型、属性名和关系名。经典的 OpenIE（开放式信息抽取）主要提取“主体、关系、客体”这样的记录。下面的练习还让模型给出实体类型、属性、关系限定信息和原文引文，方便后续核对与建图。模型可以提出“博物馆”“展览”“推出”等业务标签，程序依然可以要求它返回固定的 JSON 字段。 [OpenIE 原始论文](https://ijcai.org/proceedings/2007/429) · [Stanford OpenIE](https://www-nlp.stanford.edu/software/openie.shtml)

## 4. 用 Python 把正文放进提示词

提示词通常同时包含任务指令、输出格式和待处理原文，可以用 Markdown 小标题标出各段用途。下面把正文放在最后，提示词末尾就是正文的结束位置。另一种写法是用成对的 `<chunk>` 和 `</chunk>` 标记正文边界。两种写法里，`{{content}}` 都是 Python 要替换的占位符。用 `replace()` 生成提示词后，小标题或成对标签会随正文一起发给模型。 [Anthropic 提示词指南](https://platform.claude.com/docs/claude/use-xml-tags) · [Google Gemini 提示词指南](https://ai.google.dev/gemini-api/docs/prompting-strategies)

```python
template = """## 抽取任务
从「待抽取原文」识别对象，以及原文对这些对象的描述。
根据原文自行命名实体类型、属性和关系。名称应简洁、具体。

## 抽取规则
1. 保留实体在原文中的名称，为每个实体分配本次输出内的编号，
   如 e1、e2。类型无法判断时填 null。
2. 属性描述一个实体本身。时间、条件或范围若修饰整条关系，
   放在这条关系的 qualifiers 中。
3. 按语义确定关系的起点和终点。两者一起出现，只能作为线索。
4. 保留日期的原文精度。在属性值或关系的 qualifiers 中保留原文的
   否定、计划、转述等含义。无法准确保留时，省略该项。
5. 遇到“该机构”“它”等表达，只有上下文能明确指向某个实体时才合并。
6. 每项属性和每条关系附上逐字复制的原文 quote。
   如果判断依赖上下句，可以连续引用多句。缺少原文依据的内容省略。

## 输出格式
只返回一个 JSON 对象，包含 entities 和 relations 两个数组。
- entities 每项包含 id、name、type、attributes。
- attributes 每项包含 name、value、quote，无属性时返回 []。
- relations 每项包含 from、type、to、qualifiers、quote。
- from 和 to 引用 entities 中的 id。
- qualifiers 是一个对象，没有限定信息时返回空对象。
- 没有抽到实体或关系时，对应数组返回 []。

## 待抽取原文
{{content}}
"""

content = "青禾博物馆于2025年3月推出城市记忆展。该展览免费开放。"
prompt = template.replace("{{content}}", content, 1)
print(prompt)
```

如果采用成对标签，可以将模板最后一节写成下面这样。Python 仍然替换 `{{content}}`。

```text
<chunk>
{{content}}
</chunk>
```

模板里的 `e1`、`e2` 是**本次抽取的临时编号**，用来让 `from` 和 `to` 引用同一次输出里的实体。不同 Chunk 都可能出现 `e1`，合并时要先识别实际对象，再使用图谱中的实体 ID。若某种判断反复出错，可以把原文与完整的预期 JSON 放到待处理正文之前。这叫 **few-shot（少样本示例）**。例如用“林晨参加了客户支持部的例会”演示为何不能从共现推出任职。 [Anthropic 提示词示例指南](https://platform.claude.com/docs/claude/use-xml-tags)

## 5. 读懂展览示例的预期输出

输入是「青禾博物馆于2025年3月推出城市记忆展。该展览免费开放。」下面是供核对的预期 JSON。

```json
{
  "entities": [
    {
      "id": "e1",
      "name": "青禾博物馆",
      "type": "博物馆",
      "attributes": []
    },
    {
      "id": "e2",
      "name": "城市记忆展",
      "type": "展览",
      "attributes": [
        {
          "name": "开放方式",
          "value": "免费开放",
          "quote": "青禾博物馆于2025年3月推出城市记忆展。该展览免费开放。"
        }
      ]
    }
  ],
  "relations": [
    {
      "from": "e1",
      "type": "推出",
      "to": "e2",
      "qualifiers": {
        "时间": "2025年3月"
      },
      "quote": "青禾博物馆于2025年3月推出城市记忆展。"
    }
  ]
}
```

| 要判断的事 | 在结果里怎么表示 |
| --- | --- |
| **开放方式是谁的属性？** | 「开放方式」是属性名，「免费开放」是属性值。它描述城市记忆展，因此放在展览的 `attributes` 里。 |
| **2025 年 3 月修饰什么？** | 原文说博物馆何时推出展览，因此时间放在「推出」边的 `qualifiers` 里。原文只给了月份，保持月份精度。 |
| **“该展览”指谁？** | 它回指上一句的城市记忆展。识别不同表述是否指同一对象，叫**共指消解**。属性的 `quote` 引用两句，第一句确认身份，第二句支持属性值。 |
| **关系的方向怎么看？** | 「推出」的主体是博物馆，客体是展览，所以 `from` 是 e1，`to` 是 e2。 |

## 6. 从模型输出到可入图记录

程序可以先检查 JSON 是否能解析、边两端的 ID 是否存在，以及每段 `quote` 是否真的出现在输入里。再核对**语义**，也就是引文有没有支持输出的对象、方向和限定信息。比如原句是“博物馆拟于 2025 年 3 月推出展览”，引文即使完全一致，也只能支持计划中的推出。类似地，“参加例会”即使能定位到原文，也不足以证明任职。

多个 Chunk 汇入同一张图时，还要对齐两类东西。**实体对齐**判断不同写法是否指同一个对象，例如两个 Chunk 分别使用“青禾博物馆”和有明确出处的简称“青禾馆”。**关系名称归一**判断不同标签是否能统一，例如“推出”“举办”“开办”有时意思接近，也可能分别指首次发布和实际组织活动，需要看原文。保存原始标签和引文，后续才能核对归一是否合理。

入图时，还可以把原文引文与文档 ID、版本、Chunk ID 或原文坐标一起存起来。查询阶段就能沿关系找回文本，逐条说明答案依据。 [图谱构建与原文证据](document-to-graph.md) · [GraphRAG 两跳检索与原文引用](graph-rag-query.md)
