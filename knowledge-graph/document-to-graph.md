# 知识图谱入门：一份文档怎样变成一张可追溯的图

本文用两份虚构的企业文档贯穿全程。先从《员工目录》得到“林晨任职于客户支持部”，再把《部门负责人名单》接进来，回答“林晨所在部门的负责人是谁”。每走一步，都检查三个问题：图里新增了什么、为什么这样判断、怎样回到原文验证。

## 1. 先看懂图里有什么

```text
(林晨 · E017) ──任职于──→ (客户支持部 · D012)
```

| 术语 | 在本例中的意思 |
| --- | --- |
| 实体（Entity） | 业务上可区分、可引用的具体对象。现实中的林晨是一个员工实体，客户支持部是一个部门实体。 |
| 概念（Concept） | 对一类事物或一个业务主题的抽象理解。“员工”“部门”是概念，“客户支持”也可以是知识分类里的主题概念。具体的客户支持部是某家公司的组织单位。 |
| 类或类型（Class / Type） | 模型用来给对象分类的定义。这里定义 `员工` 和 `部门` 两类。 |
| 实例（Instance） | 某个类的具体成员。林晨是 `员工` 的实例，D012 是 `部门` 的实例。 |
| 节点（Node） | 图里的一个结构单元。业务实体可以用节点表示，文档、原文片段和任职记录也可以按需要建成节点。 |
| 关系类型（Relationship Type） | 对一种连接的命名和定义。例如 `任职于` 表示员工在某部门任职。 |
| 边（Edge） | 某次具体连接在图里的表示。E017 指向 D012 的 `任职于` 边是该关系类型的一次实例化。 |
| 属性（Property） | 附着在对象或连接上的字段和值。例如员工的入职日期、任职边的生效日期。 |
| 标识符（Identifier） | 用来识别对象的值。例中的 E017 要放在公司的员工编号体系里理解。同名的人可能有不同编号，同一人也可能在不同系统中有不同编号。 |

这里采用**属性图**的视角，节点可以有标签和属性，边有方向、类型，也能带属性。另一种常见表示是 **RDF**，其基本单位是“主语、谓语、宾语”三元组，例如“林晨、任职于、客户支持部”。RDF 中的宾语也可以是字符串、日期等字面值。两种表示都可以描述这个例子，任职日期和证据如何挂载要随表示方式选择。 [Neo4j 图数据库概念](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/) · [W3C RDF 三元组](https://www.w3.org/TR/rdf11-concepts/#section-triples) · [W3C OWL 入门](https://www.w3.org/TR/owl2-primer/)

## 2. Schema 是什么？先给图写一张规则表

**Schema（模式）是对图谱数据结构和约束的约定。** 可以把它当作一张业务规则表，写明允许记录哪些对象、对象有哪些字段、什么类型的对象可以通过哪种关系相连。项目可以用表格、代码、配置文件或约束语言表达这份约定。下面就是本例的一份 Schema。

| 对象或关系 | 允许的结构 | 本例的约定 |
| --- | --- | --- |
| 员工 | 节点 | 有内部 ID，允许姓名、员工编号、入职日期。源文档没给员工编号时，可以保留待对齐的提及。 |
| 部门 | 节点 | 有内部 ID，允许正式名称、部门编号及带适用范围的别名。 |
| 任职于 | 员工 → 部门 | 可带生效日期、结束日期和陈述状态。正式入图时保留可回查的证据。 |
| 负责 | 员工 → 部门 | 表示员工担任该部门负责人。可带有效时间或名录的适用范围，保留证据。 |

“`任职于` 从员工指向部门”是规则，“林晨任职于客户支持部”是按规则存进去的一条记录。规则还要定义业务含义，例如“林晨曾到客服部协助培训”里两个对象的类型都合规，但“协助培训”不足以支持 `任职于`。**结构校验回答格式是否合规，证据核验回答原文是否支持，实体对齐回答说的是哪个对象。** 三者在构建过程中分别检查。 [Datawhale 知识图谱基础教程](https://github.com/datawhalechina/team-learning-nlp/blob/master/KnowledgeGraph_Basic/task01.md) · [Neo4j 图谱构建器的 Schema](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html)

项目里说“Schema”可能具体指**抽取 Schema**或**存储 Schema**。前者约定模型输出什么，例如只允许抽取 `任职于` 与 `负责`，并要求返回支持这条关系的片段。后者约定写入时的数据结构及可执行的约束，例如员工业务标识在一个命名空间内唯一。有些业务规则需要应用代码或人工校验。**本体（Ontology）**进一步明确业务概念的含义和它们之间的语义关系，例如定义“部门属于组织单位的一类”，从而能够推出“客户支持部也是组织单位”。本体可以为 Schema 提供业务定义，项目中两个词的使用范围有时会重叠。 [W3C OWL 入门](https://www.w3.org/TR/owl2-primer/) · [Neo4j GraphAcademy 图谱构建课程](https://graphacademy.neo4j.com/courses/llm-knowledge-graph-construction)

## 3. 单份文档从原文走到图

假设文档 A 是《员工目录》v1。以下句号和标点也是示例原文的一部分。

| 句子 ID | 原文 |
| --- | --- |
| A1 | 林晨（员工编号 E017）于 2024 年 5 月 6 日入职。 |
| A2 | 自 2025 年 1 月 1 日起，林晨任职于客户支持部（部门编号 D012）。 |
| A3 | 该部门在本目录中也称“客服部”。 |

### 3.1 保留原文与定位，再把文本送去抽取

处理文档时，给它分配稳定的文档 ID，例如 `doc-a`，并给这次内容分配版本 `v1`。解析后保留段落、句子或表格坐标，再选取合适的上下文发给抽取程序。**Chunk（文本块）**是系统一次处理或检索的文本单位，里面可以有多个句子。本例可以把 A1–A3 放在同一个块里。只给 A2，容易丢掉林晨的员工编号。只给 A3，“该部门”的所指就可能丢失。

PDF 或扫描件的抽取文本通常还会经过版面解析或 OCR（把图像中的文字转成可处理的文本）。如果后续要高亮原件，应在这一步保留页码、区域或与原件的映射。句子在解析文本中的字符位置，和它在原件上的页面区域，是两种可以互相配合的定位方式。 [微软 GraphRAG 索引流程](https://microsoft.github.io/graphrag/index/default_dataflow/) · [W3C 文本证据定位模型](https://www.w3.org/TR/annotation-model/#text-position-selector)

### 3.2 从文本中找“提及”，再判断它指的是谁

**提及（Mention）**是某处原文里的字词或短语，用来指向一个对象。实体是被指向的对象。同一个林晨在 A1 和 A2 中各出现一次，这两处有各自的位置，后面可以指向同一个员工实体。

| 出处 | 文本里找到的内容 | 可以先作出的判断 |
| --- | --- | --- |
| A1 | 林晨、E017、2024 年 5 月 6 日 | “林晨”是员工提及，“E017”是该员工的编号，日期是入职日期。 |
| A2 | 林晨、客户支持部、D012、2025 年 1 月 1 日 | 两个对象的候选提及、一个部门编号，以及这次任职的起始日期。 |
| A3 | 该部门、客服部 | 前者是指代，后者是目录里给出的别名。 |

**命名实体识别（NER）**常用于找出人名、机构名等文本范围并给它们标类别。遇到编号可以用文本格式和“员工编号”等字段名联合识别，日期也可以用规则或模型识别后统一成 `YYYY-MM-DD`。**共指消解（Coreference Resolution）**是判断多个表达是否指向同一对象，例如根据上下文把 A3 的“该部门”指回 A2 的客户支持部。**消歧（Disambiguation）**是在多个可能对象之间排除歧义，例如用 E017 区分两位叫林晨的员工。**实体链接（Entity Linking）**是把某处提及连到图谱或主数据里的具体 ID，例如把 A2 的“林晨”连到员工 E017。一次链接可以用到共指、消歧和业务规则。 [Datawhale《Easy NLP》信息抽取](https://github.com/datawhalechina/easy-nlp/blob/main/docs/ch3/ch3.md) · [肖仰华知识图谱分享文字整理](https://developer.cloud.tencent.com/article/1367349)

### 3.3 从“有两个人或组织”走到“原文表达了一种关系”

**关系抽取（Relation Extraction）**是识别原文在说哪两个对象有什么联系。A2 中，“任职于”将“林晨”与“客户支持部”连接，“自……起”提供这条联系的生效时间。可以先产出一条候选记录。

| 候选字段 | 取值 | 判断依据 |
| --- | --- | --- |
| 主体 | A2 中的“林晨” | 句子里的任职者，编号要结合 A1 判断。 |
| 关系类型 | 任职于 | A2 有明确关系表达。 |
| 客体 | A2 中的“客户支持部” | 林晨任职的部门，A2 直接给出 D012。 |
| 生效日期 | 2025-01-01 | 日期修饰这段任职；A1 的入职日期描述另一件事。 |
| 结束日期 | 未知 | A2 只提供起始日期。 |
| 证据 | A2，另以 A1 辅助确认主体 | A2 支持任职、时间和部门编号，A1 支持员工身份。 |

实际可以按文本形态组合方法。员工表格可以按列名取值，句式稳定的通告可以用模板或规则，表达较灵活的正文可以用专门的抽取模型或让大语言模型按 Schema 返回结构化字段。模型输出首先作为候选，程序检查字段类型、原文范围、关系方向和编号冲突，必要时交给人工判断。文本重现也值得单独核验。一段引文即便能在文档中找到，还要检查它是否支持这个关系和它的限定条件。 [东南大学公开知识图谱课程大纲](https://github.com/npubird/KnowledgeGraphCourse) · [Neo4j GraphAcademy 图谱构建课程](https://graphacademy.neo4j.com/courses/llm-knowledge-graph-construction)

用几个近似句子检验边界。

| 原文表达 | 怎样解释 |
| --- | --- |
| “林晨参加了客户支持部的例会。” | 两个对象在一句话里出现，文本支持参会，任职状态仍未知。 |
| “林晨曾在客户支持部任职。” | 可以提取历史任职；具体日期和当前任职状态仍未知。 |
| “林晨未在客户支持部任职。” | 这是一个带否定的陈述。若业务需要记录，保留否定状态和上下文，正向任职查询要排除。 |
| “拟安排林晨下月到客户支持部任职。” | 记录为计划或待确认状态。“下月”要依赖文档日期解析，不能直接作为已经生效的任职。 |
| “林晨在客户支持部和研发部任职。” | 可有两个候选关系。兼任是否成立、是否需要角色区分，要结合业务规则和上下文核验。 |

一个基本自查问题是：句子里哪个词支持关系，哪个词决定它已生效、已结束、被否定还是处于计划中？答不出来时，先把候选和证据保留下来。

### 3.4 对齐实体，分别处理三种重复

**实体对齐（Entity Resolution）**是判断来自同一份或不同文档的记录是否描述同一个实际对象。它在工程上可以分成三步：先找可能匹配的对象，再根据编号、类型、组织与上下文比较，最后决定自动链接、暂缓或人工核验。若对齐两个数据源，主数据是组织认可的人员或部门名录，可以用来核对编号和有效期。实践里，**命名空间**指一个编号有意义的范围，例如“这家公司的人事系统的员工编号体系”。本例用“编号体系 + 对象类型 + 编号”作为业务身份键，再映射到图内部 ID。若编号可能重用，还需要来源定义和有效期。 [Neo4j 工程教程 Entity Resolved Knowledge Graphs](https://neo4j.com/blog/developer/entity-resolved-knowledge-graphs/) · [ACM Queue 工业级图谱实践](https://queue.acm.org/detail.cfm?id=3332266)

- A1 的“林晨”有 E017，先按员工编号体系定位或建立员工节点。A2 的“林晨”没有重复写 E017，本例凭相邻目录条目和一致上下文连到同一节点。若目录里还有一位林晨，应查看条目边界、员工编号、上下文或主数据，缺证据时保留候选。
- A2 的“客户支持部”有 D012，先按部门编号体系定位或建立部门节点。A3 在上下文中指回这个节点，再记录“客服部”作为别名，并保留“本目录”这个适用范围及 A2、A3 的依据。
- 匹配分数可以来自名称、别名、组织路径等信号，用来排序候选。一个高相似度的名字仍可能属于另一个人。两个来源给出不同编号时，应先判断是否属于不同编号体系，或其中一个来源有误。重要的自动合并要保留原始 ID、合并依据和审核结果，便于修正误连。

这里有三种容易混在一起的去重。

| 去重对象 | 典型情形 | 处理方式 |
| --- | --- | --- |
| 实体 | A1 和 A2 都出现“林晨” | 两个提及保留，各自连到 E017。两位同名但编号不同的员工分别建节点。 |
| 业务陈述 | 两份文档都提到 E017 从同一日期开始在 D012 的同一段任职 | 核实同一任职记录及其限定条件后，可以共享一条业务陈述，并保留两份证据。若离岗后再次入职同一部门，需要区分两段任职。 |
| 证据 | A2 落在两个重叠的 Chunk 中，抽取器分别返回同一句 | 按文档 ID、版本、原文定位等信息识别同一出处。两份文件引用同一公告时，可分别保留出处并记录转载关系，避免将它们当成两条独立佐证。 |

任职陈述的识别键可来自业务系统里的任职记录 ID。缺少该 ID 时，主体、关系、客体、生效日期和角色可参与比较，时间或角色缺失时要防止误合并。“结束日期未知”和“仍然在任”也要区分。重新处理同一版本，应能够复用已识别的陈述和证据。引入新版时应重新核验受影响的关系，并保留历史版本或它与当前状态的对应关系。 [Neo4j 实体消解课程与规则定制](https://graphacademy.neo4j.com/courses/genai-graphrag-python/4-customisation/4-resolving-entities) · [智源社区《知识图谱实践指引》](https://hub.baai.ac.cn/view/31635)

### 3.5 给每条陈述挂上能返回原文的证据

**陈述（Statement）**是某个来源作出的一项可记录的主张。**限定条件（Qualifier）**补充它适用于哪个时间、角色或范围。**证据（Evidence）**是支持它的原文与定位信息。**来源追溯（Provenance）**还关心它从哪份文档、哪个版本、经什么抽取和审核步骤进入图谱。用这些字段可以回答“谁说的、原文在哪儿、这句话具体支持什么”。 [Wikidata Statements 中的限定条件和引用](https://www.wikidata.org/wiki/Help:Statements)

把 A 落成下列业务对象与证据。

| 图谱记录 | 支持它的原文 | 证据说明 |
| --- | --- | --- |
| 员工 E017 的姓名为林晨，入职日期为 2024-05-06 | A1 | A1 给出姓名、员工编号、入职日期。 |
| 部门 D012 的名称为客户支持部 | A2 | A2 在部门名称后提供编号。本例用该名称作为图上的展示名。 |
| 部门 D012 的目录内别名为客服部 | A2、A3 | A2 提供被指代的部门，A3 提供别名及范围。 |
| 陈述 R001 为 E017 任职于 D012，生效日期为 2025-01-01 | A2、A1 | A2 支持关系、生效时间及部门身份。A1 辅助确认 A2 中的人是 E017。 |

例如，为 R001 建立证据记录 EV001。用 `doc-a / v1 / A2` 指向该句，保存整句作为展示证据。在句内按 Unicode 码点计数时，位置 `[18, 28)` 对应“林晨任职于客户支持部”，可供界面高亮。位置从 0 开始，包含起点、排除终点，坐标基于本例表格里的 A2 原文，包括空格与全角标点。验证完整陈述仍需展示整句，因为时间和编号在高亮范围外；验证员工身份再展开 A1。实际项目还应说明位置是相对于句子、段落还是全文，文本修改后使用对应的版本重新定位。保留精确引文及前后文也有助于回查重复句子。 [W3C Text Position Selector](https://www.w3.org/TR/annotation-model/#text-position-selector) · [W3C Text Quote Selector](https://www.w3.org/TR/annotation-model/#text-quote-selector)

一种轻量实现是在任职边上放陈述 ID，在独立证据表中保存一个或多个出处。另一种是在图中把任职陈述建成记录节点，分别连接员工、部门和证据。任职有多段历史、带角色、需要保存审核状态或有多份证据时，记录节点能让这些信息有明确归属。微软 GraphRAG 的公开输出也有可供参考的出处链，关系记录可经 `text_unit_ids` 找到文本单元，再经 `document_id` 返回源文档。本文另外给出了句内坐标，便于展示更细的证据。 [Neo4j GraphAcademy 中间节点建模](https://graphacademy.neo4j.com/courses/modeling-fundamentals/8-adding-intermediate-nodes/) · [微软 GraphRAG 输出字段](https://microsoft.github.io/graphrag/index/outputs/)

可以把单份文档的处理过程复述成一句话：保存带版本的原文，按业务规则抽取候选，把提及连到已核实的实体，再把每条陈述和它依赖的原文、身份依据与限定条件一起存下来。

## 4. 第二份文档怎样接进来

文档 B 是同一家公司的《部门负责人名单》v1。

> B1：客服部（部门编号 D012）的部门负责人为周宁（员工编号 E021）。

1. **独立抽取。** 在 B1 识别部门“客服部 / D012”和员工“周宁 / E021”。原句把部门放在前面，根据 Schema 将关系规范成“周宁 `负责` 客服部”，方向为员工到部门，保留 B1。
2. **对齐部门。** 核对 A 和 B 使用的是同一家公司的同一套部门编号，且 D012 在适用范围内指同一组织。将 B1 的部门提及链接到已存在的 D012。A3 的别名解释了两个名字为何不同，同一编号体系下的 D012 提供更强的身份依据。
3. **写入另一条边。** 创建或复用 E021，并将“E021 `负责` D012”写入图中。B1 没给负责人的起止日期，可保留名单的版本、发布日期或适用范围；发布日期与任职开始日分别保存。

```text
《员工目录》A2（A1 辅助确认身份）       《部门负责人名单》B1
                ↓                                ↓
       林晨 E017 ──任职于──→ D012 ←──负责── 周宁 E021
                            客户支持部
                            目录别名 客服部
```

文档之间的桥是共同实体 D012。可以沿 A 的陈述找到 D012，再从同一节点找到 B 的陈述。是否额外保存文档之间的直接连接，要看有没有引用、修订或其他明确的文档级关系。共享一个部门节点本身，只说明两份资料都提到了同一个部门。

如果 B 只写“客服部”，可以用组织路径、别名范围、日期和主数据缩小候选。多个候选仍成立时，保留待确认状态。如果两份名单对同一时期的负责人给出不同结果，应分别保存原始陈述和来源，核对时期、角色、版本与来源权威性。两份名单可能记录的是不同任期，也可能存在待处理的冲突。 [Neo4j 实体对齐工程教程](https://neo4j.com/blog/developer/entity-resolved-knowledge-graphs/) · [中国计算机学会《工业规模的知识图谱》译文](https://www.ccf.org.cn/c/2020-02-04/694736.shtml)

## 5. 图谱怎样回答两跳问题

**一跳**是沿一条边到达相邻节点。“林晨所在部门的负责人是谁？”可以拆成两步。

1. 从 E017 沿 `任职于` 找到 D012，查看 A2；必要时用 A1 核对员工身份。
2. 从 D012 反向查入边 `负责` 找到 E021，查看 B1。这里反向查找的是已存的“E021 负责 D012”。

当任职陈述和负责人名单在问题所要求的时间范围内同时适用，可以回答“林晨所在部门是客户支持部，名单所列负责人是周宁”，并分别引用 A2 与 B1。题目如果问“现在”，例文需要再补充足以确认现状的时间信息。如果追问“周宁是林晨的直属上级吗”，需要直属汇报关系的原文或一条明确适用的组织规则，部门负责人身份本身不足以推出直属关系。

**GraphRAG** 可以用图帮助检索：先从问题识别“林晨”，找到候选实体，再按问题扩展相关的边和节点，最后取回支撑每一跳的文本给生成模型。图负责找连接，原文负责提供回答所需的证据。不同 GraphRAG 实现的索引与查询策略各有侧重，此处展示的是围绕一个实体和具体关系展开的查询方式。 [微软 GraphRAG 索引流程](https://microsoft.github.io/graphrag/index/default_dataflow/) · [微软 GraphRAG 输出字段](https://microsoft.github.io/graphrag/index/outputs/)

## 6. 用这些问题复述一遍

| 回顾问题 | 回答应覆盖什么 |
| --- | --- |
| 什么是 Schema？ | 用 `员工 → 任职于 → 部门` 说明类型、方向、字段和证据要求；再给出 E017 到 D012 的具体实例。 |
| A2 没写 E017，怎么知道“林晨”是谁？ | A2 给出提及，A1 和目录条目提供身份依据；若存在同名候选，要继续消歧。 |
| 为什么要分别对齐实体、去重陈述、去重证据？ | 三者的合并单位分别是实际对象、业务主张、原文出处；合并其中一个层次仍可保留其他层次的不同记录。 |
| 如何证明图里的“任职于”带着正确的日期？ | 返回 `doc-a / v1 / A2` 整句，检查“自……起”的修饰对象；只高亮关系短语会漏掉时间。 |
| 两份文档怎样支持两跳问答？ | 先验证它们说的是同一个 D012，再按关系方向组合两条边，检查时间适用范围，并给每跳配原文。 |
